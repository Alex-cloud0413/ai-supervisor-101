## 3. 讲清楚：怎么选对毕业选题 + 10 项毕业验收打分表

### 3.1 选对第一个项目的 3 条铁律 + 3 类职场选题库

新手做第一个真实项目最容易犯的错，是贪大求全——一上来就要做「全公司 ERP 系统」。记住第一件成品的黄金标准：**「单次耗时 15–60 分钟、每周至少重复 1 次、输入输出格式稳定、最好是绿灯或脱敏后的黄灯数据」**。

照下面 3 类高成功率职场选题库直接对号入座：

| 选题类别 | 典型职场痛点举例 | 输入 / 输出 | 数据安全处理（3.4 课） | 推荐定时方案（5.3 课） |
|---|---|---|---|---|
| **① 表格清洗与固定口径汇总** | 每周一要把 5 张渠道导出表合并、过滤测试单、按品类算客单价出汇总 Excel | 输入：`data/*.xlsx` 或 `.csv`<br>输出：`output/周汇总.xlsx` | **红/黄灯原表严禁喂云端**：只给 AI 看表头 + 2 行假数据写脚本，全程本地 Python 跑 | 手动跑或本机系统定时（\$0 Token） |
| **② 零散文档 / 周报结构化归纳** | 把一周随手记在 `notes/` 里的 10 篇零散备忘或会议纪要，整理成老板爱看的 300 字周报 | 输入：`notes/*.md`<br>输出：`output/本周周报.md` | 删去人名/薪资/NDA 细节，关闭工具的「上传 Session Log」开关 | DeepSeek Harness「自动化任务」（周五 17:00，需要 AI 动脑总结） |
| **③ 公开情报与动态自动追踪** | 像 `ai-radar` 一样，每天追踪公开行业榜单、官方公告或关注开源工具的最新版本更新 | 输入：公开接口 / RSS / Atom<br>输出：`output/daily-radar.md` | 🟢 纯绿灯公开数据，放心练习与归档 | GitHub Actions `schedule`（关电脑也跑）或 DSH 工作日定时 |

### 3.2 10 项毕业监工验收打分表（达到 8 分即毕业，安全红线一票否决！）

项目跑通之后，别急着庆祝——像验收外包项目一样，逐项给自己打分：

| # | 验收项 | 对应课程 | 合格标准（满足打 1 分） |
|---|---|---|---|
| 1 | **标准目录分区** | 3.1 | `data/`（只读）、`scripts/`、`output/`、根目录 `README.md` 边界清楚 |
| 2 | **依赖与环境隔离** | 3.2 | 有 `.venv` 和精确更新的 `requirements.txt`（未乱装几百兆无用大库） |
| 3 | **参数抽离进配置** | 3.3 | 会变的汇率、关键词、文件路径、追踪列表都放在 `*.yaml` 配置里 |
| 4 | **配齐 `AGENTS.md`** | 5.2 | 根目录有一份 40–80 行的 `AGENTS.md`，写清验收命令与红线 |
| 5 | **先计划后动手** | 5.1 | 动手改代码前用四要素需求单 + `/plan` 审过书面方案 |
| 6 | **安全红线零失误（一票否决）** | 1.3 / 3.4 | `.gitignore` 拦住了 `.env`、`.venv/`、`output/`；代码与文档零硬编码密钥；未把红灯隐私表裸奔传云端 |
| 7 | **Git 留痕与 `diff` 验收** | 4.1–4.3 | 在独立分支开发，经 `git diff --stat` 与逐行核对后干净合入 `main` |
| 8 | **异常与边界兜底** | 2.8 / 5.1 | 遇到空行、404、断网超时不会直接报错崩溃，能吐出人话中文提示 |
| 9 | **私有 GitHub 备份** | 4.4–4.5 | 代码与配置已推送到自己的私有 GitHub 仓库（确认不含敏感产物） |
| 10 | **实测跑通与定时策略** | 5.3 | 终端退出码为 `0`、产出文件肉眼核验无误，并按需配好定时或记清运行命令 |

## 4. 现场看：兑现 5.1 伏笔——`release_radar.py` 毕业样板实测走通全流程

在 5.1 课里，我们审完了「新增开源仓库 Release 追踪」的 `/plan` 实施计划。现在作为毕业项目样板，我们在**不改动原有 `build_top10.py`、`daily_briefing.py` 和 `config.yaml`**（以保护 M2–M3 实测引用）的前提下，按同一套 6 步规范落出了两个独立文件：

1. **人类可调的配置面板**：[`practice/release-radar.yaml`](../../../practice/release-radar.yaml)（共 9 行）：

```yaml
# ai-radar 毕业项目（M6）扩展配置：开源工具版本追踪清单
output_file: release-radar.md
timeout_seconds: 10
repos:
  - deepseek-ai/deepseek-harness
  - openai/codex
  - astral-sh/uv
```

2. **零新增依赖的 Python 脚本**：[`practice/scripts/release_radar.py`](../../../practice/scripts/release_radar.py)——只用 Python 标准库 `urllib.request` + `xml.etree.ElementTree` 和项目已有的 `PyYAML`，一行 `requirements.txt` 都不用多加！

### 一次极具教学价值的真实插曲（监工必须会处理！）

我们在云端虚拟机第一次直接试跑 `python3 practice/scripts/release_radar.py` 时，碰上了一个极其真实的生产环境坑：**在公司共享出口 IP 或云端环境下，免 Token 调 `api.github.com` 很容易撞上 `HTTP 403` 速率限流！**

- **糟糕的脚本**：直接红字崩溃，整份简报生成失败；
- **合格的毕业脚本**：第一时间优雅降级并给出中文提示；更进一步，我们在脚本里加了一层**官方公开 Atom 订阅源兜底**（`https://github.com/{repo}/releases.atom`——免 Token、不占 REST API 限额！）。

加上兜底后重新实测运行 `python3 practice/scripts/release_radar.py`，终端干脆返回：

```text
已生成开源版本追踪简报：output/release-radar.md（成功 3/3）
```

打开实测生成的 `practice/output/release-radar.md`：

## 5. 你来读：帮一位同学做毕业答辩，找出这份仓库里丢分的 3 个硬伤

一位同学做完了自己的毕业项目「每周竞品动态追踪器」，准备推上 GitHub 交作业，你帮他扫了一眼项目情况：
- 根目录摆着 `README.md`、`AGENTS.md`、`config.yaml`、`requirements.txt`、`.env`、`data/`、`scripts/run.py`、`output/本周汇报.md`。
- `.gitignore` 里只写了 `.DS_Store` 和 `__pycache__/`。
- `scripts/run.py` 跑通了正常网页，但还没测过「某个竞品网站临时打不开」时会不会整条脚本崩溃；并且他在 `main` 上直接连改了 6 轮、期间一次都没 `git commit`。

停下来想 10 秒：对照 3.2 节的 10 项打分表，你必须立刻拦下哪 **3 个** 硬伤（其中哪 1 个触发一票否决）？

**判断思路**：
1. **触发一票否决的安全红线（第 6 项）**：`.gitignore` 漏写了 `.env`、`.venv/` 和 `output/`！现在推上 GitHub 会直接把真实 `.env` 密钥泄露出去，必须先补齐 `.gitignore`（加 `!.env.example`）并用 `git status` 核查确认 `.env` 未被跟踪。
2. **缺少异常兜底测试（第 8 项）**：没测过目标网页超时或 404 的场景，周一定时一跑极可能因为单个网站打不开导致整份报告中断；应让 AI 给抓取逻辑加上 `try / except` 超时跳过与中文提示，并拿一个错误网址实测一遍。
3. **缺少小步 Git 存档与分支保护（第 7 项）**：连改 6 轮没打过一次存档，等于全程没系安全带；立刻整理干净并打下基线 `commit`，以后加新功能先开 `feat/` 分支再改。

## 6. 小检查（3 道判断题）

1. 做自己的第一个职场毕业项目时，应该尽量挑「每周重复、规则明确、数据可控」的小切口，先把完整 6 步闭环跑通，再逐步扩展功能。（对 / 错）
2. 只要脚本在正常网络和正常表格下跑通了一次，就不需要测试超时、404 或空字段等异常情况了。（对 / 错）
3. 毕业验收打分表里，「安全红线（不泄露 `.env` 密钥、不把红灯敏感原表裸奔上传云端）」属于一票否决项，任何情况下都不能妥协。（对 / 错）
