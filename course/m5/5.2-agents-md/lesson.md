# 5.2 `AGENTS.md`：给 AI 的项目说明书

> 学习目标：理解 `AGENTS.md` 的自动加载机制（全局层 vs 项目层）与跨工具通用价值，能照着「5 板块骨架」写出自己项目的 `AGENTS.md`，把每次新会话都要重复叮嘱的规矩一次固化下来。
>
> 演示环境：DeepSeek Harness `0.2.2-rc.5`（对应官方文档 `agent-instructions` 机制），直接拆解配套仓库新增的真实文件 `practice/AGENTS.md`（共 46 行），该文件将在 M7 迁移到 OpenAI Codex 时直接原样复用。

---

## 1. 为什么每次新开对话，你都要把同样 6 句话重新嘱咐一遍？

5.1 课我们学会了写四要素需求单和用 `/plan` 审计划。但用过一周后，你会立刻碰上一个新的烦心事：

- 今天新开一个会话，得叮嘱一句：「别动 `data/` 里的原始快照，汇率写进 `config.yaml`，商用模型记得过滤 `:free` 和 `:batch`。」
- 明天又新开一个会话，忘了叮嘱那句，AI 顺手把新参数硬编码进了 `.py`，改完也没跑脚本自检就汇报「已完成」。

在公司里带新人，你不会每天早上把部门制度重新口述一遍，而是发一份《**岗位操作手册（SOP）**》放在工位最显眼的地方。在 AI 编程工具里，这份专门放在项目根目录、每次新会话自动塞到 AI 眼前的「AI 入职手册」，就叫 **`AGENTS.md`**。

---

## 2. 系统位置：`AGENTS.md` 在你开口说话之前，就自动装进了 AI 的脑子

对比一下 **`README.md`**（3.1 课）和 **`AGENTS.md`**（本课）的分工：`README.md` 是**给人看**的；`AGENTS.md` 是**给 AI 看**的，每次在工作区开启新对话时，执行框架（Harness）都会自动把它读进系统提示词里：

```
你在 ai-radar 工作区点「新会话」
      ↓
DeepSeek Harness / Codex 自动按两层顺序加载说明书：              ← 【本课位置】
  ① 用户全局层：~/.dsh/AGENTS.md（你跨项目的个人习惯，如「用简体中文汇报」）
  ② 项目根层  ：ai-radar/AGENTS.md（本项目的目录规矩、验收命令、绝对红线）
      ↓
你发出简洁需求（不用再把老规矩重说一遍！）
      ↓
AI 带着这些规矩干活 → 你用 /plan 和 git diff 验收
```

> **顺手认全兄弟文件名**：`AGENTS.md` 是 DeepSeek Harness、OpenAI Codex、Cursor 等主流工具共同支持的开放约定（社区规范站 [agents.md](https://agents.md/)）；如果你以后碰到 Anthropic 的 Claude Code，它默认认的同名文件叫 **`CLAUDE.md`**。常见省心做法是：**正文只维护一份 `AGENTS.md`**，在根目录放一个只有一行字的 `CLAUDE.md` 写明「请遵循 `AGENTS.md`」，一套规矩通吃所有工具——7.1 课切到 Codex 时，我们就会直接复用今天这份 `practice/AGENTS.md`！

## 3. 讲清楚：一份好用的 `AGENTS.md` 只需要写这 5 块

新手写 `AGENTS.md` 最容易走两个极端：要么不写，要么把几千字的公司制度全粘贴进去。根据实践经验，**把篇幅压在 40–80 行（1 屏左右）、全写具体可检查的规矩**，AI 遵守得最稳。

直接对照 5 个固定板块，缺一不可也无需贪多：

| 板块 | 核心作用 | 应该写具体什么（好例子） | 千万别写成什么（无效空话） |
|---|---|---|---|
| **① 项目定位与目录分工** | 让 AI 3 秒认清文件放哪 | `data/` 只读原料仓、`scripts/` 正式脚本、`config.yaml` 参数面板、`output/` 可再生成品 | 「项目结构清晰合理」 |
| **② 运行与自检命令** | 强迫 AI 改完自己先跑通再交卷 | 贴出精确命令 `python3 scripts/daily_briefing.py`，要求汇报退出码和命中条数 | 「改完请认真测试」 |
| **③ 代码与配置约定** | 守住长期一致的业务口径 | 可变参数统一放 `config.yaml`；商用比价过滤 `~`、`:free`、`:batch`；新增库同步更新 `requirements.txt` | 「写出优雅高质量代码」 |
| **④ 绝对红线（严禁触碰）** | 划出最不能踩的底线 | 绝不改 `data/` 原文件；绝不硬编码密钥或提交 `.env`；跨文件大改先出计划再动手 | 「注意信息安全」 |
| **⑤ 协作与交付习惯** | 让验收对你最省力 | 大改动先开 `feat/` 或 `agent/` 分支；完成后列出 `git diff --stat` 与验收步骤 | 「做好版本管理」 |

### 写 `AGENTS.md` 的 3 条黄金守则

1. **只写「能一眼判对错」的具体规矩**：把「注意数据准确」改成「商用比价必须排除 `:free` 和 `:batch` 后缀」——后者 AI 立刻照办，你也 1 秒就能在 `git diff` 里核验。
2. **宁短勿长，绝不塞成千行大百科**：DSH 官方配置对指令链设有字节预算上限（`maxBytes`），文件越冗长，真正关键的红线越容易被稀释；大型项目若某个子目录有特殊规矩，再单独在子目录下放一份精简子 `AGENTS.md` 按需加载即可。
3. **像养宠物一样「踩一次坑，补一条规矩」**：不用第一天追求完美。以后只要发现 AI 犯了某个低级错（比如把导出文件名写错、忘了保留表头中文），就在 `AGENTS.md` 里顺手添上一行，下次它就再也不犯。

**最常见的误解**：以为「只要把『绝不删文件、绝不传密钥』写进 `AGENTS.md`，就万无一失了」。**记住这个边界**：`AGENTS.md` 是「**员工手册（软约束）**」，不是「**门禁铁锁（硬约束）**」——模型在极长对话里偶尔仍可能走神漏看某条提示。真正兜底的硬防线永远是：**1.5 课的工作区权限审批 + 3.4 课的 `.gitignore` 与 `.env` 隔离 + 4.1 课的 Git 存档！**

## 4. 现场看：逐块读完 `ai-radar` 的真实 `practice/AGENTS.md`

配套仓库已经正式新增了一份 46 行的真实 [`practice/AGENTS.md`](../../../practice/AGENTS.md)，下面完整展示它的核心内容，你可以直接复制改造成自己的项目说明书：

```markdown
# AGENTS.md — ai-radar 项目说明书

本文件写给在本项目（`ai-radar`）中工作的 AI 编程工具（DeepSeek Harness、OpenAI Codex、Claude Code 等）。开始任何修改前，请先读完本文件。

## 1. 项目定位与目录分工
- `data/`：公开免 Key 数据快照（OpenRouter + Hacker News）。**只读原料仓**。
- `scripts/`：正式可复用 Python 脚本（`fetch_snapshots.py`、`build_top10.py`、`daily_briefing.py`）。
- `config.yaml`：人类可读的参数控制面板（汇率、排除前后缀、HN 热度门槛与关键词）。
- `output/`：脚本生成的成品目录，可随时重算，不进 Git。
- `requirements.txt` / `.env.example`：第三方库清单与密钥空模板。

## 2. 运行与自检命令
修改代码或配置后，必须用项目虚拟环境实测跑通对应脚本，再汇报完成：
- `python3 scripts/build_top10.py`
- `python3 scripts/daily_briefing.py`
验收时请向我汇报：实际运行的命令、终端退出码、输出文件路径，以及本次命中的模型条数与热点条数。

## 3. 代码与配置约定
1. 参数与逻辑分离：汇率、关键词、追踪仓库列表统一写进 `config.yaml`，不硬编码进 `.py`。
2. 数据口径一致：商用比价必须继续过滤 `~` 前缀、`:free` / `:batch` 后缀及价格 `<= 0` 条目。
3. 依赖同步更新：新装第三方库必须同步更新 `requirements.txt`。
4. 保持中文输出清晰：报错提示、简报标题和 `config.yaml` 注释使用简洁中文。

## 4. 绝对红线（严禁触碰）
- 绝不修改或覆盖 `data/` 下的原始快照文件（除非明确要求刷新快照）。
- 绝不把任何真实 API Key 或 Token 写进代码、`config.yaml` 或提交进 Git。
- 绝不提交 `.env`、`.venv/` 或 `output/`；不要运行 `git reset --hard`、`rm -rf` 等不可逆命令。
- 涉及跨文件修改或新增功能时，先出书面计划并等我确认，再动手改文件。

## 5. 协作与交付习惯
- 做大改动前优先在独立分支（如 `feat/...` 或 `agent/...`）操作，不要直接破坏 `main`。
- 完成后简要列出修改的文件清单（如 `git diff --stat`），说明如何验证。
```

回头对照一下 5.1 课实拍的 `/plan` 审批截图你会发现：轨迹第一行就自动打出了 **`上下文注入 · AGENTS.md`**！正是因为工作区里躺着这份 `practice/AGENTS.md`，AI 甚至不用等我们反复提醒，就在计划里主动遵循了「参数放 `config.yaml`、不碰 `data/` 原文件、改完跑 `daily_briefing.py` 自检」全套规矩！

## 5. 你来读：帮同事揪出这份新手 `AGENTS.md` 里的 4 个大坑

同事学完后兴奋地给自己的「月度销售报表工具」写了一份 `AGENTS.md`，发你帮忙把关：

```markdown
# AGENTS.md
1. 请务必写出非常优雅、高可用、符合工业级最佳实践的 Python 代码。
2. 调用大模型接口时直接用我的真实 Key：MY_SECRET_KEY_DEMO_ONLY_9988，省得每次问我。
3. 下面粘贴了我们公司 2024–2026 年共 600 行财务报销制度全文，请逐字牢记：
   （此处省略 600 行……）
4. 改完代码直接帮我 `git push --force` 推到公司主仓库就行，不用告诉我细节。
```

停下来想 10 秒：这 4 条里藏着哪 **4 个** 典型反面教材？

**判断思路**：
1. **第 1 条全是无效空话**：什么叫「优雅」「工业级」？AI 根本没法量化。应该删掉空口号，换成具体可核查的规矩（比如目录分工、列名口径、运行命令）。
2. **第 2 条触发最高安全红线！** `AGENTS.md` 通常是要提交进 Git 仓库的普通文档，把真实 API Key 写进去等于把银行卡密码贴在大门口！立刻删掉并吊销这把 Key，改写「密钥一律从本地 `.env` 读取」。
3. **第 3 条严重塞爆上下文**：把 600 行无关制度全塞进 `AGENTS.md`，既白白消耗每次对话的 Token 额度，又会稀释真正核心的红线；应该只提炼跟脚本直接相关的 3–5 条计算口径。
4. **第 4 条反其道放开了高危红线**：`git push --force` 会直接覆盖冲掉历史提交，而且跳过验收汇报等于撤掉了监工岗位！应该改成「大改先开分支、完成后展示 `git diff --stat` 和自检结果，由我确认后再提交推送」。

## 6. 小检查（3 道判断题）

1. `README.md` 主要写给人类看，`AGENTS.md` 主要写给 AI 编程工具看；在 DeepSeek Harness 和 OpenAI Codex 里开启新会话时，工具会自动读取项目里的 `AGENTS.md`。（对 / 错）
2. 为了让 AI 什么都懂，写 `AGENTS.md` 越长越好，最好把公司几百页的规章制度和你的 API Key 都直接粘进去。（对 / 错）
3. 只要把「绝不删除重要文件」写进了 `AGENTS.md`，就可以放心把工具权限开成全自动放行，不需要再看审批弹窗或做 Git 存档了。（对 / 错）
